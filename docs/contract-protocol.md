# Kurabase contract protocol v1

Implementation: [`contracts/src/KurabaseSchema.sol`](../contracts/src/KurabaseSchema.sol).
The ABI generated by `forge build` is authoritative; tuples below preserve its field order.

## Authority and the execution trust boundary

An instance has a root owner. The owner can appoint developers. The owner or a
developer can explicitly grant one or several gateway addresses execution access.
An application gateway additionally needs a session signed by the user or a
separate, instance-configured identity authority. An API key identifies/routes a
project; it is not an independent source of database authority.

The contract checks gateway delegation and the independently signed session. The
gateway evaluates SQL, RLS, constraints, and functions within that session. The
developer and user entrust this SQL execution to their authorized gateway. The
contract does **not** interpret SQL policies or prove that a gateway's plan
matches its SQL request. A compromised delegated gateway can misexecute data
writes during a valid session. It cannot forge another user's session or use an
ordinary session to change catalog metadata, policies, functions, or migrations.
This is delegated execution, not cryptographic SQL-policy enforcement.

User sessions grant database data-execution authority for the stated instance,
gateway and lifetime. They do not contain per-table restrictions or per-statement
approval, and may be reused until expiration/revocation. RLS applies the finer
permissions in the trusted SQL layer. Merely signing a session with a different
`uid` or fabricated admin claims does not create that identity or authority.

Owner/developers may write through `executePrivileged` without a user session.
A gateway may use that method only when explicitly granted `privileged=true`.
That is the service/admin credential path and bypasses user-session checks by
design. Keep its signer separate from the ordinary application gateway signer.
Even a privileged gateway cannot grant itself developer/owner status, appoint
identity authorities, or modify gateway grants.

All canonical chain data is public. Read RLS supplies application visibility,
not confidentiality. Gateway-issued JWTs are not accepted by the contract as
proof of another user's identity.

## Deployment and administrative calls

```solidity
constructor(address initialOwner, address initialIdentityAuthority)
setDeveloper(address developer, bool enabled)                // owner only
setGateway(address gateway, bool enabled, bool privileged)   // owner/developer
setIdentityAuthority(address authority, bool enabled)       // owner/developer
transferOwnership(address nextOwner)                        // owner only
isGatewayAuthorized(address gateway) view returns (bool)
isIdentityAuthorityAuthorized(address authority) view returns (bool)
gateways(address gateway) view returns (bool enabled, bool privileged, uint256 epoch)
```

Zero identity authority disables externally attested identities initially; EOA
wallet sessions still work. An enabled identity-authority address cannot also be
an enabled gateway, enforcing separate signing identities.

Each gateway update increments its epoch, invalidating all sessions for the
previous grant. A gateway's grant records its delegating administrator and that
administrator's epoch. Revoking or updating that developer, or transferring away
from the owner that issued a grant, invalidates its dependent gateway grants.
Reappointing the developer does not revive old grants; explicitly grant again.
`gateways(...).enabled` is raw metadata; use `isGatewayAuthorized` for effective
permission. Identity-authority grants record the issuing administrator and its
epoch as well: revoking/replacing that developer or transferring ownership
invalidates authority signatures and authority-initiated revocation powers.
Reappointing the developer does not revive those authority grants; explicitly
grant again. `identityAuthorities(...).enabled` is raw metadata; use
`isIdentityAuthorityAuthorized` for effective permission. Individual session
revocation and user nonce floors provide permanent revocation.

## Signed user sessions

```solidity
struct Session {
    address gateway;
    address user;
    bytes32 uid;
    bytes32 claimsHash;
    uint256 expiresAt;
    uint256 nonce;
    uint256 gatewayEpoch;
}
```

EIP-712 domain:

```json
{
  "name": "KurabaseSchema",
  "version": "1",
  "chainId": "the RPC chain ID",
  "verifyingContract": "the instance contract address"
}
```

The exact primary type is:

```text
Session(address gateway,address user,bytes32 uid,bytes32 claimsHash,uint256 expiresAt,uint256 nonce,uint256 gatewayEpoch)
```

`expiresAt` is a Unix timestamp in seconds and is exclusive: a session expires
when `block.timestamp >= expiresAt`. `gatewayEpoch` must equal the current grant's
epoch. The chain and instance are bound by the EIP-712 domain. Sign the typed-data
digest directly; do not apply an additional `personal_sign` prefix. Signatures
are 65 bytes `r || s || v`, low-s only, with `v` equal to 27 or 28. EIP-1271 smart
contract wallets are not implemented in v1.

Two identity paths are supported:

1. **Self-signed EOA:** the recovered signer equals `session.user`, `uid` is its
   address left-padded with zero bytes to bytes32, and `claimsHash` is zero. The
   user cannot self-assert arbitrary application IDs or extra claims.
2. **Independent identity authority:** the recovered signer is effectively
   authorized by `isIdentityAuthorityAuthorized`, including an active issuing
   administrator and matching delegation epoch. It attests the complete session, including the
   application `uid`, user address and claims commitment, after its own external
   login/identity verification. That login service is trusted to establish the
   real user's authority and must not be controlled by the gateway's signer.

`uid` and `user` must be nonzero. The UID is an opaque 32-byte identity at the
contract boundary. A SQL adapter must define and consistently use its mapping to
application `auth.uid()` values; wallet mode does not magically produce a UUID.

The contract treats `claimsHash` as an opaque commitment. If the gateway exposes
`auth.jwt()`, it must validate the exact provided claims payload against that
commitment before using it. A concrete adapter convention is
`keccak256(UTF8(claimsJson))`, with the exact signed JSON string transmitted
unchanged. Parse JSON only after matching the bytes; reserializing before hashing
can change the digest. Empty wallet claims use the zero hash.

```solidity
sessionDigest(Session session) view returns (bytes32)
hashSession(Session session) view returns (bytes32) // identical alias
verifySession(Session session, bytes signature) view returns (bytes32 digest)
revokeSession(Session session)
revokeUserSessions(address user, uint256 minimumNonce)
```

Read authentication uses `verifySession`; it validates the designated gateway's
effective grant, signature, expiry, nonce, and revocation without requiring the
RPC caller to equal the gateway. The HTTP service must separately check that
`session.gateway` equals its configured gateway. Validate against a block at
least as fresh as the query's pinned snapshot; do not indefinitely cache a
successful authentication after revocation. `execute` additionally requires
`msg.sender == session.gateway` and rechecks everything at commit time.

A user, the designated gateway, an administrator, or an effectively authorized identity authority may
revoke an individual session digest. A user, administrator, or effectively authorized identity authority
may increase that user's minimum nonce, invalidating all lower-nonce sessions.
Nonce floors cannot decrease. Nonces are **session generations**, not one-use
transaction counters; global state revision prevents replay of a stale plan.

## WritePlan ABI and deterministic digest

```solidity
struct Operation {
    uint8 kind;
    bytes32 tableId;
    bytes32 rowId;
    bytes32 columnId;
    bytes data;
}

execute(uint256 expectedRevision, Operation[] operations, Session session, bytes signature)
    returns (bytes32 planHash)
executePrivileged(uint256 expectedRevision, Operation[] operations)
    returns (bytes32 planHash)
hashPlan(uint256 expectedRevision, Operation[] operations, bytes32 actorContextHash)
    view returns (bytes32)
```

The digest is exactly:

```solidity
keccak256(abi.encode(
    block.chainid,
    address(this),
    expectedRevision,
    actorContextHash,
    operations
))
```

Use ordinary Solidity ABI encoding, **not** packed encoding, JSON serialization,
or native Rust layout. The argument ABI types are
`uint256,address,uint256,bytes32,(uint8,bytes32,bytes32,bytes32,bytes)[]`.
`actorContextHash` is the EIP-712 session digest for `execute`; for privileged
execution it is `keccak256(abi.encode(executorAddress))`. Operation order and
every data byte affect the hash. Adapters normalize their catalog and value bytes
before constructing operations. The executor stores opaque bytes and deliberately
does not depend on a particular SQL engine or Rust serialization format.

[`contracts/test-vectors.json`](../contracts/test-vectors.json) supplies fixed
chain/instance/session/plan inputs and expected hashes for independent Rust and
JavaScript codec tests. The Solidity suite checks these hashes against values
generated with the off-chain `cast` ABI encoder.

| Kind | Operation | Required fields and behavior |
| --- | --- | --- |
| 0 | PutCatalog | `tableId=rowId=0`, nonzero `columnId` is catalog key; store exact `data`, including empty bytes. Admin/service scope only. |
| 1 | DeleteCatalog | Same key fields, empty `data`; catalog key must exist. Admin/service scope only. |
| 2 | InsertRow | Nonzero table/row IDs, `columnId=0`, empty `data`; row must not exist. |
| 3 | SetCell | Nonzero table/row/column IDs; row must exist; store exact `data`. |
| 4 | DeleteCell | Nonzero table/row/column IDs, empty `data`; row must exist. Unsetting an absent cell is allowed. |
| 5 | DeleteRow | Nonzero table/row IDs, `columnId=0`, empty `data`; row must exist. |
| 6 | MarkMigration | `tableId=rowId=0`, nonzero `columnId` is version key, nonempty `data` holds version text; version key must not be applied. Admin/service scope only. |

Adapters should use `keccak256(UTF8(version))` as the migration version key and
the unchanged version string as its bytes. The contract tracks version keys;
the delegated SQL executor remains responsible for deriving consistent keys,
validating schema/table/column dependencies, and preserving migration order.
Migration history stores applied version, not a content hash. DDL/DML operations
and the migration marker belong to one batch; a failure rolls all of them back.

`rowId` is a stable internal identity, independent of an application primary key.
Application PK updates must retain `rowId`. On delete/reinsert the contract
increments an internal generation so old cells cannot become visible again.
Missing cells and stored SQL NULL remain distinct: `getCell` returns an existence
flag plus opaque bytes, and the SQL value codec determines the NULL encoding.

## Concurrency, atomicity, and resource limits

`revision()` starts at zero. Every successful nonempty batch increments it once,
regardless of the number of operations. Each affected row's version becomes that
new revision. The caller must plan all reads against the same complete snapshot
at `expectedRevision`. If any canonical data/catalog mutation commits first,
the whole stale plan fails with `TransactionConflict(expected,actual)`.

This deliberately coarse optimistic lock covers negative and predicate reads
as well as existing rows. It prevents two independently planned UNIQUE/FK or
set-based writes from both committing against an outdated assumption. It does not
verify that a trusted gateway actually evaluated those constraints correctly.
The gateway must replan on conflict; it cannot merely replace the revision on
the same unvalidated operation list.

Each batch permits 1–1024 operations, additionally bounded by EVM gas and RPC
limits. Solidity revert semantics ensure a later failing operation reverts all
earlier state writes and events. There are no external calls during application,
and no partial success result. Long session-bound SQL transactions and production
reorg/finality handling are outside this contract's scope.

## Rebuilding the projection

Replay logs from the deployment block in `(blockNumber, transactionIndex,
logIndex)` order, checking the emitting contract address. The operation event is:

```solidity
event OperationApplied(
    uint256 indexed revision,
    uint256 index,
    uint8 kind,
    bytes32 tableId,
    bytes32 rowId,
    bytes32 columnId,
    bytes data
);
event PlanCommitted(
    uint256 indexed revision,
    bytes32 indexed planHash,
    address indexed executor,
    address user,
    bytes32 uid,
    bytes32 claimsHash,
    bytes32 actorContextHash
);
```

Only `revision` is indexed on `OperationApplied`; table/row/column IDs are in ABI
event data. Apply each catalog/row/cell/migration operation to staged projection
state. Insert resets that row's cells; delete removes its projected cells.
`PlanCommitted` terminates each successful plan and records its actor and digest.
Publish an immutable snapshot only after all logs in its block are processed;
do not expose intermediate operations or transactions as a completed block.
Empty blocks still advance the block snapshot, even though revision stays fixed.

Catalog includes serialized definitions needed to reconstruct tables, policies,
functions, views and migrations. Materialized query results are derived gateway
state and are not stored here. Events contain exact new values, so reconstruction
does not require gateway-local backups. The contract does not enumerate mapping
keys; deployment-block event replay is the normal inventory source.

Read helpers:

```solidity
revision() view returns (uint256)
catalog(bytes32 key) view returns (bytes)
catalogExists(bytes32 key) view returns (bool)
appliedMigrations(bytes32 version) view returns (bool)
rowExists(bytes32 tableId, bytes32 rowId) view returns (bool)
rowVersion(bytes32 tableId, bytes32 rowId) view returns (uint256)
rowGeneration(bytes32 tableId, bytes32 rowId) view returns (uint256)
getCell(bytes32 tableId, bytes32 rowId, bytes32 columnId)
    view returns (bool exists, bytes data)
```

Administration emits `OwnershipTransferred`, `DeveloperChanged`,
`GatewayChanged`, `IdentityAuthorityChanged`, `SessionRevocation` and
`SessionNonceChanged`. Such changes do not increment relational revision;
session/delegation checks read their current state at authentication/commit time.

## Errors and gateway mapping

Stable Solidity errors include `Unauthorized`, `InvalidSession`, `SessionExpired`,
`SessionRevoked`, `InvalidSignature`, `TransactionConflict`, `InvalidOperation`,
`RowAlreadyExists`, `RowNotFound`, `CatalogNotFound`, `MigrationAlreadyApplied`,
`InvalidAddress` and `ResourceLimit`. The HTTP layer maps these to stable public
authentication/privilege/conflict/execution errors instead of leaking raw RPC
stack traces. SQL RLS/constraint failures are normally rejected before submission
by the gateway and must leave chain state unchanged.

## Build, test, and local deployment

Run from `contracts/`:

```sh
rtk proxy forge build
rtk proxy forge test
```

The standalone test suite requires no `forge-std` checkout and includes forged
session attempts, domain/gateway binding, revocation and scope tests, event
payload replay checks, atomic rollback, stale revision conflicts, and randomized
cell/session tests (256 runs per fuzz test).

For a local Anvil chain, provide `OWNER_PRIVATE_KEY` and `GATEWAY_ADDRESS` through
the environment. Optional `IDENTITY_AUTHORITY_ADDRESS` enables an independent
login issuer; optional `SERVICE_GATEWAY_ADDRESS` receives explicit privileged
execution scope. Keep private keys out of committed files and shell command text.
Then run:

```sh
rtk proxy forge script script/Deploy.s.sol:Deploy --rpc-url http://127.0.0.1:8545 --broadcast
```

This command submits deployment and delegation transactions to the specified
local RPC. `contracts/broadcast/` contains the resulting addresses and receipts.
Configure the gateway with the instance address, chain ID, deployment block and
its own signer. Use the owner or separately authorized service signer for
migrations; the normal gateway has no catalog-writing authority.
