GETTING STARTED

Run Kurabase against a local Anvil chain

The shortest path is a local chain, a gateway, and a publishable key created by that gateway. Command names may evolve while the implementation is under active development.

1. Start Anvil

anvil --chain-id 31337

Keep Anvil running. It provides a deterministic local EVM node; its accounts and all values are disposable development fixtures.

2. Apply a migration

create table posts (
  id bigint primary key,
  author_id uuid not null,
  title text not null
);
alter table posts enable row level security;

Submit each migration as a versioned, atomic unit. The @kurabase/cli runner reads the secret only from its environment, skips applied versions, and records a migration only after success.

export KURA_SECRET_KEY='server-only-secret'
kura migrate --url http://127.0.0.1:54322 --dir supabase/migrations
kura sql --url http://127.0.0.1:54322 --query 'select * from posts'

Never pass a secret key as a command-line flag or include it in browser code.

3. Connect the Console or SDK

Open the Console, enter the gateway URL and publishable key, then add a gateway-validated bearer token when you need caller identity. The token must derive from a self-signed wallet or configured identity-authority session; the gateway cannot create it. Secret server keys are for privileged server-side/admin actions only and must not be placed in a browser build.

Known limitations

Kurabase does not provide a PostgreSQL wire protocol, full PostgreSQL semantics, durable availability guarantees, realtime subscriptions, storage, or privacy for public-chain data. SQL-language RPC functions support scalar, SETOF/table, and atomic mutating functions. Procedural functions and unsupported SQL return explicit errors rather than silently approximating behavior.
